>> a memory you can measure

MQ-AI is a local assistant that runs from a USB drive: a model runtime, a chat page, search over a shelf of PDFs, and an image pipeline. Until this week it forgot everything when a chat closed. The goal was to make it learn. That word needs care. The weights do not change. Nothing is fine-tuned. What can change is what the model reads before it answers.

So the memory is notes. Short Markdown files in a git repository, one lesson each, with a line saying how it was verified. A small profile is always included in the prompt. Everything else is retrieved per question. A local model may propose notes from a conversation, but proposals land in an inbox that is never searched. A note becomes memory only when a person approves it, and every approval is a commit. It is the learn loop with a smaller surface.

Storage turned out to be the easy part. The hard part is deciding when memory should be used at all. Ranking always returns something. Ask for the capital of Australia and the three closest notes are still three notes, and a model given them will try to use them. Similarity scores from embedding models sit in a narrow band, so a fixed threshold does not separate relevant from unrelated. The gate instead compares the best score with a baseline: how similar the question is, on average, to a dozen neutral sentences. Memory is used only when the best note beats that baseline by a margin. Otherwise the model answers without it.

The margin came from measurement, and the measurement is the part I would keep if everything else were thrown away. It is a file of questions, each paired with the note that should answer it, plus questions that should get no note at all. Every new note adds two questions, phrased in different words from its title. One command reruns the set, sweeps the margin, and lists every miss.

It caught a decay I would not have noticed. With the first embedding model, the right note reached the prompt for most questions while memory was small. As notes were added, that share fell from 85 to 64 percent. Nothing broke. Answers just got quietly worse. Moving memory to bge-m3 lifted it to 94 percent, and it has held as the notes grew to thirty: 63 of 66 relevant questions get their note, and 6 of 8 unrelated questions correctly get none. Switching models means rebuilding the index, and search now refuses to compare vectors from two different models instead of returning confident nonsense.

The smaller findings are about writing. A title in ordinary words is found more often than one in technical terms. With bge-m3 the body counts too. A note about a copied signature was not recalled for "why did the new image get a signature in the corner?" A better title barely moved it. One sentence describing the symptom the way you would ask about it did. Two notes about the same thing push each other down the list. Merging them helps. Changing the expected answer in the test only flatters the test.

The limits are plain. The questions are written by the same person who writes the notes, so the numbers measure consistency, not truth. Most findings rest on one example. Still, the model is the same as it was last week. What changed is a folder of text, a gate, and a test that shows when either gets worse. That is what learning means here: something written down, approved, and checked.
