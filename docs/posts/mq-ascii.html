>> mq-ascii

ASCII art looks like a trick. It is a short chain of ordinary decisions. Shrink the image until each pixel is one cell. Reduce each cell to a single brightness value. Divide that range into buckets. Give each bucket a character, from dense to sparse. Most converters hide the chain and show only the result. MQ-ASCII shows the chain.

Point at any cell on the screen and the pipeline below follows it: the source pixel, the resized pixel, its luminance, the bucket it fell into, the character it received. Nothing is summarised. Every number on the page is the number the renderer actually used.

The details are where the honesty is. Characters are taller than they are wide, so the height has to be divided by an aspect ratio or every image comes out stretched. Dividing brightness by 25 gives eleven buckets, but the last one only covers six values. Rec.601 and Rec.709 weight red, green and blue differently, and the page counts how many cells change character when you switch. None of this is visible in the finished picture. All of it shapes the picture.

A dark terminal inverts the problem. Bright pixels need dense characters, or the image prints as its own negative. A single checkbox reverses the ramp, and the bucket readout shows the subtraction it performs.

Color does not change the shape. The color branch picks exactly the same character as the grayscale branch and wraps a 24-bit ANSI code around it. The form carries the brightness. The escape sequence carries the hue. Seeing the two branches side by side makes that separation obvious in a way the output alone never does.

The page also writes the Python script that would produce the same result with the current settings. That is the part that matters most. A tool that explains itself should be reproducible outside itself. The browser is where you look. The terminal is where you keep it.
